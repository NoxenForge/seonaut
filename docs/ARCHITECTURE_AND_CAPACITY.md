# 运行架构、拆分方案与容量建议

记录日期：2026-10-16。源码基线：`a67387fe63a291be2ba49dd02399f20e453eb8b5`。

[返回文档目录](README.md) · [尖叫蛙能力差距清单](SCREAMING_FROG_GAP_ANALYSIS.md) · [容器开发指南](DEVELOPMENT.md)

本文汇总当前运行方式、前后端拆分可行性，以及 2 核 2GB 内存服务器的保守容量建议。“当前实现”来自源码与本机容器核对；“建议”尚未实施，也不代表实测容量。

## 1. 当前运行模式

SEOnaut 是使用 **Go HTML 模板进行服务端渲染的单体 Web 应用**。浏览器请求页面后，由 Go 查询数据、渲染模板并返回 HTML。

```text
浏览器
  │ HTTP：页面、静态资源、表单、导出
  │ WebSocket：抓取进度
  ▼
Go 应用进程
  ├─ HTML 模板渲染、CSS / JS 等静态资源
  ├─ 登录、项目管理、报告查询与导出
  ├─ 爬虫调度、HTTP 抓取、页面解析
  └─ SEO 问题分析
  │
  ▼
MySQL（独立容器）
```

- 前端使用 HTML 模板、自定义 CSS 和少量原生 JavaScript，图表使用 ECharts。
- 页面大多通过服务端渲染和表单交互；抓取进度通过 `/crawl/ws` 推送。
- 当前没有独立的 Vue/React 前端工程，也没有足以直接支持独立前端的完整 JSON API。不能将 `web/templates` 当作可独立部署的静态前端。
- 爬虫与 Web 服务处在同一个 Go 应用进程中，爬虫队列与运行状态也在进程内存中。抓取及问题分析会与页面请求共享 CPU、内存和数据库连接。
- MySQL 已经可以独立部署；应用通过数据库连接配置访问它。

源码依据：`internal/routes/app.go:23` 注册页面、静态文件和 WebSocket 路由；`internal/services/renderer.go:57` 使用 `html/template` 渲染页面；`internal/routes/project.go:16` 查询后生成页面；`internal/services/crawler.go:70` 在应用内启动抓取；`internal/crawler/queue.go:28` 管理内存队列。

## 2. 当前本机环境

以下是 2026-10-16 的本机运行快照，端口和容器名可能随配置改变，并非线上部署现状。

| 环境 | 访问地址 | 容器组成 | 用途 |
|---|---|---|---|
| 普通运行环境 | `http://localhost:9000` | `seonaut-app` + `seonaut-db` | 运行已经构建好的应用 |
| 开发环境 | `http://localhost:9001` | `seonaut-dev_app_1` + `seonaut-dev_assets_1` + `seonaut-dev_db_1` | 本机编辑源码、容器内构建和运行 |

开发环境的工作方式：

- 源码挂载到容器；Go、Air、Node.js、esbuild 和 MySQL 在容器内运行，本机无需直接安装这些依赖。
- `app` 容器通过 Air 监听 Go、HTML 模板、翻译和配置变化，自动重新编译并重启。当前使用 `go build -race`，带竞态检测开销。
- `assets` 容器只通过 esbuild 监听和构建 CSS 等资源，**不是一个对浏览器提供页面的独立前端服务**。
- 生成的静态资源仍由 Go 应用提供。CSS 或模板修改后需刷新浏览器；后端重启会中断当前抓取。
- 开发环境的 MySQL 对本机映射为 `127.0.0.1:13306`；容器间使用 `db:3306`。数据库凭据保存在被 Git 忽略的本地配置中，不记录到本文。
- 生产 Dockerfile 使用多阶段构建，Node.js 只用于构建静态资源，最终运行镜像不需要常驻 Node.js 服务。

配置依据：`compose.dev.yaml`、`dev/Containerfile`、`dev/air.toml`、`Dockerfile`。日常命令见 [容器开发指南](DEVELOPMENT.md)。

## 3. 前后端是否可以拆分

可以，但应区分以下三种目标。

| 目标 | 当前可行性 | 需要处理的内容 |
|---|---|---|
| MySQL 独立容器或独立服务器 | 已支持 | 配置数据库连接与网络 |
| CSS、JS、图片交给 Nginx / CDN | 可改造 | 静态资源路径、缓存与部署；HTML 仍由 Go 渲染 |
| 独立 Vue/React 前端 + Go API | 需要应用改造 | JSON API、前端页面、登录鉴权、错误响应、分页筛选、导出及 WebSocket 适配 |

### 3.1 如果目标是重新设计界面

建议保留 Go 爬虫、分析规则及数据访问逻辑，为项目管理、报告和扫描控制补充 JSON API，再用独立前端承接页面。

可采用同域部署：静态页面由 Nginx 提供，`/api/` 和 WebSocket 由反向代理转发给 Go。这样可以减少跨域配置；仍需明确 Session Cookie、请求校验与 WebSocket 鉴权策略。若采用跨域前端，应另行设计 CORS 和 Cookie 行为。

这属于后续改造方案，**当前尚未提供上述完整 API，也未重写前端**。迁移时可以按页面逐步替换，避免一次重做全部功能。

### 3.2 如果目标是提高扫描容量

优先考虑 **Web/API 与爬虫 Worker 分离**。前端静态化主要改变界面交付方式，对抓取、解析和数据库分析的资源消耗帮助有限。

未来可按“Web/API → 持久化任务队列 → Worker → 数据库”的方向拆分，并解决任务状态、进度推送、取消、失败恢复、历史数据和全局并发控制。当前没有独立 Worker 服务，不能仅增加几个应用副本就认为获得了可靠的分布式抓取能力。

进程或容器拆分本身不会增加一台 2 核 2GB 主机的资源。若目的是扩容，需要让 Worker 或数据库使用额外机器资源。

## 4. 并发的含义

“支持多少并发”至少有三个不同含义：

1. **网站任务并发**：同时扫描几个项目。
2. **请求并发**：每个项目同时工作的 HTTP 抓取 worker 数。
3. **访问用户并发**：同时浏览页面、查询或导出报告的用户数。

以下建议针对前两项，不能据此推导能支持多少在线用户或固定 QPS。用户并发需要另外测试报告查询与导出负载。

## 5. 源码中已确认的限制和资源特点

| 项目 | 当前实现 | 依据 |
|---|---|---|
| 每项目 HTTP 抓取 worker | 固定为 2 | `internal/crawler/crawler.go:26`、`:272` |
| 请求间等待 | 每个 worker 请求前随机等待 0～1499ms | `internal/crawler/crawler.go:23`、`:305` |
| 抓取总时长 | 2 小时上下文超时 | `internal/crawler/crawler.go:29`、`:108` |
| 单次 HTTP 请求超时 | 10 秒 | `internal/services/crawler.go:21`、`:190` |
| 页面报告数量阈值 | 20000；不是实测安全容量 | `internal/services/crawler.go:19` |
| 项目并发限制 | 同项目防止重复启动；不同项目没有全局数量限制 | `internal/services/crawler.go:170` |
| URL 队列 | 保存在进程内存中，随发现链接增长 | `internal/crawler/queue.go:28` |
| 数据库连接池 | 最多 25 个打开连接、25 个空闲连接 | `internal/repository/sql.go:13` |
| 响应体读取 | 先完整读入，再限制用于解析的数据为 10MB；不是响应体内存硬上限 | `internal/services/html_parser.go:24`、`:32`、`:40` |
| 数据库及容器限制 | 当前 Compose 未显式配置内存预算或 MySQL 缓冲池调优 | `docker-compose.yml`、`compose.dev.yaml` |

因此，启动两个不同项目通常会建立合计 4 个常规抓取 worker，但不能据此认定整套服务所有 HTTP 活动都严格限制在 4 个连接内。请求响应时间、下载、解析、数据库写入和随机等待共同决定实际吞吐量；“2 worker”不等于“每秒抓 2 页”。

## 6. 2 核 2GB 的保守部署建议

前提：Linux 主机总共 2 核、2GB 内存，应用与 MySQL 共用资源；运行构建好的生产镜像，无 Chromium 渲染，无其他明显占用资源的业务。**本次没有在这一规格主机上做压测，以下不是性能保证或最大支持数量。**

| 使用场景 | 建议起始方式 | 说明 |
|---|---|---|
| 当前普通 HTML 抓取 | 同时 1 个项目、每项目 2 个 worker | 作为保守起点，仍需观察真实站点负载 |
| 页面小、链接少、站点规模小 | 单项目稳定后，压测尝试同时 2 个项目、合计 4 个 worker | 未验证通过前，不作为正式容量承诺 |
| 万页站、大响应体、链接密集或开启存档 | 同时 1 个项目，重点观察峰值内存和磁盘 | 页面数不是唯一决定因素；存档和后处理也要测试 |
| 未来增加 Chromium / JavaScript 渲染 | 从 1 个渲染页面开始验证 | 2GB 会较紧张，不能保证浏览器与 MySQL 共存时稳定 |

运营上建议先采用“同一时间只启动 1 个扫描任务，其他任务等待”的策略。但**当前没有实现全局排队和任务数限制**，需要人工控制或后续开发，不能理解为配置已经生效。

不要用本机开发环境的数据直接推算生产容量：开发环境含 Air、编译器、CSS 监听和 Go `-race` 开销；macOS 的容器运行时还涉及虚拟机资源分配。当前本机同时运行的两套实例也不代表它们可以在同一台 2GB 服务器上稳定共存。

### 6.1 容量评估需要覆盖的阶段

- 单项目从发现 URL、抓取到问题分析全部完成，不能只测启动后的短时间流量。
- 代表性小站、万页站、大页面、链接密集站，以及存档开启和关闭。
- 抓取期间浏览报告、导出文件，观察交互是否明显变慢。
- 在单项目稳定后尝试双项目，记录应用和数据库容器内存、主机可用内存、CPU、交换空间、磁盘 I/O、数据库查询耗时、错误与任务完成情况。
- 根据峰值和资源余量决定是否提高任务数，不能仅根据平均 CPU 利用率判断。出现内存持续增长、频繁换页、OOM、数据库积压或超时，应先降低负载再定位。

可使用 `podman stats` / `docker stats` 观察容器，但还需结合主机监控。本文仅记录验证方法，尚未执行该规格下的容量测试。

## 7. 后续优先级与实施状态

1. 补全局任务数控制、项目级抓取参数与响应体读取上限，先控制单机资源峰值。
2. 调整历史明细保留策略，再补多轮逐 URL 对比和定时任务。
3. 若重点是界面定制，再逐步补 JSON API 和独立前端。
4. 若重点是扫描扩容，再设计持久化队列、独立 Worker 和跨进程进度通信。
5. 按目标站需求加入 JS 渲染、自定义提取及其他审计能力，详见 [能力差距清单](SCREAMING_FROG_GAP_ANALYSIS.md)。

以上顺序是建议，不是已经确认的开发计划。本次只整理文档，没有实施这些功能、变更运行配置或进行 commit / push。
